## 1. The observed old failure — now executed, not source-traced

PR-00 classified OB-001 from source reading. It is now reproduced by execution, in disposable
temp directories, against the pre-fix code. Two independent probes.

### Probe A — pristine baseline `store.go` taken straight from `d97809b2`

A real directory placed where `catalog.json` belongs makes `os.ReadFile` fail with a non-not-found
error on Windows:

```
BASELINE read error is: read ...\catalog.json: Incorrect function.
BASELINE unreadable: store!=nil=true err=<nil>
BASELINE unreadable: profiles seeded in memory = 3
```

`OpenStore` returned a **usable Store and a nil error** on an unreadable catalog. That is the
fall-through.

### Probe B — the destructive consequence, old decision logic, same injected-read seam

The overwrite needs "read fails, write succeeds", which a directory-in-the-way cannot produce
(renaming onto a directory fails). Driving the pre-fix branch through the same seam the regression
uses:

```
OLD: fixture catalog = 3476 bytes, collection id 1
OLD: on a permission-denied read -> store!=nil=true err=<nil>
OLD: catalog is now 3259 bytes (was 3476)
OLD: the returned store reports 0 collections (fixture had 1)
OLD: backup catalog.json.bak-20260906 = 3259 bytes
OLD: reopening from disk now finds 0 collections
```

Every step of the PR-00 trace, confirmed end to end: no error surfaced, the real catalog was
replaced by the empty three-profile one, **the day's backup captured the empty state rather than
the real one**, and the collection is gone from disk.

Both probes ran in throwaway copies of the package under the scratchpad. The owner's working tree
was never reverted, reset or overwritten.

### Correction to a PR-00 claim

**PR-00 was wrong that a zero-length `catalog.json` reached new-catalog initialization.** Verified
against pristine `d97809b2`:

```
BASELINE zero-length: store!=nil=false err=catalog.json is damaged: unexpected end of JSON input
BASELINE zero-length: catalog is now 0 bytes
BASELINE zero-length: backups created = []
```

`json.Unmarshal` rejects empty input before the schema gate is consulted, so baseline already
failed closed, left the file untouched and wrote no backup. `existed = len(b) > 0` was a latent
hazard, not a live defect. PR-01 still rejects the case — earlier, explicitly, and with an
actionable message — but must not be credited with fixing a fall-through that did not exist.
`OB_STATUS.md` carries the correction.

## 2. The change

### 2.1 Read classification (the fix)

`OpenStore` becomes a one-line delegate to a new unexported `openStore` holding the logic. The
old single `if err == nil` is replaced by an explicit three-way switch:

| Read outcome | Behavior |
|---|---|
| Success, non-empty | Parse as the existing catalog. Unchanged. |
| Success, zero-length | Refuse. Dedicated message naming the file and pointing at the `.bak-YYYYMMDD` sidecar. Returns before `json.Unmarshal`. |
| `errors.Is(err, fs.ErrNotExist)` | Initialize a new catalog. Unchanged. |
| **Anything else** | **Refuse.** Wrapped error preserving the cause; `main.go:71` turns it into `log.Fatalf`. Any bytes returned alongside the error are discarded. |

`errors.Is` is used deliberately so a wrapped or `*fs.PathError`-shaped not-found is still
recognized as absent; a test covers all three shapes.

### 2.2 Two injected boundaries, no new package-level state

```go
func OpenStore(dataDir string) (*Store, error) {
	return openStore(dataDir, os.ReadFile, nil)
}

func openStore(dataDir string, readFile func(string) ([]byte, error),
	persistObserver func(op, path string)) (*Store, error)
```

The addendum asked for an invocation-local or internal helper rather than a package-global mutable
hook. Parameters give that: no shared state, nothing to restore, no way for one test's injected
fault to reach another, and no risk to concurrent tests. `OpenStore` is the only production caller
and always passes `os.ReadFile, nil`. The three existing production callers
(`main.go:71`, `appbackup.go:438`, `migrate.go:114`) are untouched — the exported signature and
behavior are unchanged for every supported case.

Critically, injection supplies the **read result** — bytes and error together — so an injected
failure and a genuine one travel the identical switch. Nothing short-circuits ahead of the branch
under repair, which is what makes the red run below meaningful.

### 2.3 Observation seam at the authority-write boundary

One unexported `Store` field, `persistObserver`, set only through `openStore`, plus a
`notePersist(op, path)` helper. Every call site reports the attempt **before** performing it and
before any gate that could skip it.

**Coverage, stated explicitly:**

| Operation | Site | Reported as |
|---|---|---|
| Catalog publication | `writeCatalog`, first statement — ahead of both the `failSave` seam and the read-only gate | `catalog-write` |
| Daily backup creation | `dailyBackup`, before `os.WriteFile` | `backup-create` |
| Daily backup pruning | `dailyBackup`, before each `os.Remove` | `backup-prune` |
| Pre-migration backup | `backupBeforeMigrate`, before `os.WriteFile` | `pre-schema-backup` |

**Not covered, and why:** `saveJobs` (the `jobs.json` sidecar) is not instrumented. `OpenStore`
only ever *reads* the sidecar, via `loadJobs`, so no jobs write is reachable in the startup path.
Also outside the observer: `os.MkdirAll(dataDir, 0o755)` at the top of `openStore`, which runs
**before** the catalog read and is part of the initialization-intent residual in section 5.

The claim these assertions support is scoped: **zero application-initiated authority mutations in
the traced startup path**. It is not a claim that the operating system performed no I/O of any
kind — reading a file has unrelated system effects outside this contract.

## 3. Why the proposed test was not used

The addendum's three objections were checked against the code and are all correct.

| Objection | Verified | How the shipped tests handle it |
|---|---|---|
| The `catalog.json.bak-*` assertion conflicts with fixture setup | Correct. `writeCatalog` calls `dailyBackup`, and `s.lastBak` is empty in a fresh process, so the fixture's own save writes `catalog.json.bak-YYYYMMDD`. The proposed test would have failed on correct behavior | Snapshot catalog bytes **and** every `.bak-*` / `.pre-schema-*` sidecar by name and content after the fixture is persisted; then require identical membership and identical bytes. Never asserts that no backups exist. Every glob and read error is checked with `t.Fatalf` |
| An absent `.tmp` is not proof of no attempted write | Correct. `writeCatalog` renames `catalog.json.tmp` onto the target on success, so absence afterwards is equally consistent with a completed write | The `persistObserver` seam counts attempts, with a positive control proving it is wired |
| A fault hook that returns early can make the test pass without a fix | Correct | The seam injects the read *result*; both injected and real errors reach the same switch. The red run in section 4 proves the tests fail against the old logic |

The addendum also warned against requiring exact old pass counts. Section 4 compares failure
**identities and causes**, and the two known Windows failures stay named rather than hidden.

## 5. What this proves, and what it does not

| Claim | Status |
|---|---|
| Non-not-found read errors cannot trigger empty replacement | **Proved.** Three error shapes, zero attempted writes, bytes unchanged |
| Zero-length existing input cannot trigger initialization | **Proved** — and it already could not at baseline. PR-01 makes the rejection explicit and the diagnostic actionable. See the correction in section 1 |
| Invalid input and newer schema retain established behavior | **Proved.** New tests plus the four unchanged `schema_test.go` tests |
| Fresh disposable directory retains initialization compatibility | **Proved**, through both `openStore` and exported `OpenStore` |
| Missing previously initialized catalog, or an unmounted expected root, cannot be mistaken for first use | **OPEN. Not delivered.** See below |

### The initialization-intent residual (open under OB-001)

`fs.ErrNotExist` does not prove the operator intended a new catalog. A data directory that was
previously initialized but whose drive is not mounted reads exactly the same as first use. Worse,
`os.MkdirAll(dataDir, 0o755)` runs at the top of `openStore`, **before** the read — so pointing the
app at a path whose storage is absent creates the directory and then initializes a new catalog in
it. This patch does not change that, and deliberately does not try to: distinguishing the two needs
storage identity, which is a larger design decision. **Do not mark the broader
initialization/identity guarantee resolved on the strength of this narrower repair.**

### Other limitations

- **Windows only.** All evidence is windows/amd64, go1.26.4. The error shapes are injected and
  therefore platform-independent in the test, but the real-world triggers (sharing violations,
  ACL denial) and the observed `Incorrect function.` message are Windows-specific. Linux and macOS
  behavior for this path has no evidence here.
- **Race: NOT TESTED**, unchanged. No C compiler; no tools installed, no move to WSL.
- **The observer is bounded**, as stated in section 2.3. It covers four catalog-authority write
  paths, not `saveJobs`, and not `MkdirAll`.
- **OB-002 remains open.** `TestOpenStore_RecoverySaveFailureIsNonFatal` passing unchanged pins an
  existing decision; it does not certify that recovery durability is correct.
- **Nothing else was touched.** OBX-001, OBX-004, OB-002 and OB-003 are all still open and separate.
  No UI change, no `go.mod` change, no `atomicRename` change, no config-loading change, no refactor.

## 6. The actual startup diagnostic

Not a UI screen — the server is a CLI process, and `main.go:71-74` turns an `OpenStore` error into
`log.Fatalf("open catalog: %v", err)`. The operator sees, on stderr:

Unreadable catalog:

```
open catalog: cannot read C:\Users\<user>\...\catalog.json: open
C:\Users\<user>\...\catalog.json: Access is denied. — refusing to start so an unreadable
catalog is never replaced by a new empty one. Check the file's permissions, and that the
drive holding the data folder is connected
```

Zero-length catalog:

```
open catalog: C:\Users\<user>\...\catalog.json is empty (0 bytes) — that is a damaged
catalog, not a new one. Recover it from a catalog.json.bak-YYYYMMDD sidecar in the same
folder, or move the empty file aside if you really do want to start a new catalog here.
Refusing to overwrite it
```

The process exits non-zero and no HTTP listener starts, so there is no UI state to design. The
existing `READ-ONLY:` startup log for a newer-schema catalog (`main.go:88-90`) is unaffected.

### Correction 2 (F-2) — the reason given for excluding `saveJobs` from the observer was wrong

Section 2.3 says `saveJobs` is uninstrumented because *"`OpenStore` only ever reads the sidecar,
via `loadJobs`, so no jobs write is reachable in the startup path."* The second half is false.
`loadJobs` (`store.go:3370`) calls `saveJobs` (`store.go:3350`) at `store.go:3400-3401` whenever it
reconciles a job left `RUNNING` into `INTERRUPTED`, so a **successful** startup after an unclean
shutdown does write `jobs.json`.

The conclusion still holds, for a different reason. The correct justification is **control flow,
not read-only-ness**: `s.loadJobs()` is at `store.go:1283`, immediately before `return s, nil` at
`1284`, while every refusal returns earlier — `1164` (zero-length), `1172` (invalid JSON), `1183`
(unreadable). A **rejected** open cannot reach `loadJobs`, so no jobs write is reachable on the
path the "zero attempted writes" claim covers.

Sections 2.3 and 5 should be read with that substitution. `loadJobs`, `saveJobs` and config loading
are unchanged by PR-01; that fail-open family remains OBX-004.

### Correction 3 (F-1 reinforcement) — where the zero-length correction now lives

Section 1 already carries the corrected finding and remains accurate. The same correction had
**not** reached `catalog_open_test.go`, whose comments still described a zero-length overwrite path
that never existed. That is fixed in the follow-up; the production behavior is unchanged.
